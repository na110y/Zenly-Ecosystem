# P1-I011 — Đăng ký và xác minh email user

**Stage:** identity  
**Status:** DONE  
**Depends on:** 002, 010  
**Canonical modules — read fully:** P1-PUBLIC, P1-FLOW, P1-API, P1-SEC  
**Previous:** [P1-I010](./010_SCHEMA_USER_VA_SESSION_PUBLIC.md) · **Index:** [Atomic Issue Index](./00_ISSUE_INDEX.md) · **Next:** [P1-I012](./012_LOGIN_LOGOUT_VA_SESSION_USER.md)

## Objective

Triển khai `POST /api/user/register` và `POST /api/user/register/verify-email` theo `P1-API §8`, đúng state machine `REGISTERED → EMAIL_VERIFIED` tại `P1-FLOW §2`, hash password bằng Argon2id (`P1-SEC §1`), gửi email xác minh qua provider adapter (Resend, đứng sau interface theo `P1-ARCH §4`). Không triển khai login/session ở issue này (thuộc `P1-I012`).

## Allowed change surface

`server/identity/`; `server/api/user/register*`; `server/api/user/register/verify-email*`; `app/pages/account/` (đăng ký + xác minh UI tối thiểu); `prisma/` (không đổi schema — đã có ở P1-I010, chỉ dùng); `tests/`.

## Required implementation

- Module `server/identity/` với 3 lớp theo `P1-ARCH §4`: route handler mỏng (`server/api/user/register.post.ts`, `server/api/user/register/verify-email.post.ts`), use case (`server/identity/use-cases/register-user.ts`, `verify-email.ts`), repository (`server/identity/repository/user-repository.ts`), provider adapter (`server/identity/adapters/email-adapter.ts` interface + `resend-email-adapter.ts` implementation).
- `POST /api/user/register`: validate email/password/displayName bằng Zod (từ chối field lạ theo `P1-API §11`), hash password bằng `argon2` (tham số OWASP khuyến nghị hiện hành cho Argon2id — `P1-SEC §1`), tạo `User` status `REGISTERED`, tạo `EmailVerificationToken` (random 256-bit, chỉ lưu hash, `expiresAt` có hạn), gửi email xác minh qua adapter. Không tiết lộ qua response liệu email đã tồn tại hay chưa (`P1-FLOW §2` — trả cùng response thành công dạng chung, hoặc lỗi generic không phân biệt) — kiểm tra kỹ P1-API để tránh user enumeration.
- `POST /api/user/register/verify-email`: nhận token thật (không phải hash) từ client, hash lại để so khớp `tokenHash` trong DB, kiểm tra `expiresAt`/`consumedAt`, nếu hợp lệ: set `consumedAt`, chuyển `User.status` → `EMAIL_VERIFIED`, idempotent-safe khi gọi lại với token đã dùng (trả lỗi rõ ràng, không đổi state lần hai — replay phải bị từ chối theo `P1-QA §5`).
- Rate limit/CAPTCHA cho endpoint đăng ký: `P1-SEC §3` yêu cầu ngưỡng cấu hình qua `SystemSetting`, nhưng `SystemSetting` runtime rate-limit chưa có UI quản trị ở Phase này (issue rate-limit hạ tầng là `P1-I049`/`P1-I080`) — nếu chưa có cơ chế rate-limit chung, đánh dấu rõ trong evidence là giới hạn đã biết, không tự ý xây rate-limit middleware đầy đủ ở đây (tránh lấn phạm vi issue khác); tối thiểu áp constraint DB (unique email) để chặn duplicate.
- UI tối thiểu: `/account/register`, `/account/verify-email` — đủ 5 trạng thái async (`P1-PUBLIC §2`): loading, empty (n/a nếu không áp dụng), error, forbidden/disabled (n/a), success. Mobile-first, giữ SSR nếu áp dụng.
- Email content: text/HTML tối thiểu, chứa link verify — không cần thiết kế template phức tạp ở issue này.

## Tests required in the same change

- Unit: `register-user` use case — happy path tạo user + token; validate input; băm password đúng qua argon2 interface (mock chỉ ở lớp adapter provider, không mock DB).
- Unit: `verify-email` use case — chuyển state đúng; từ chối token hết hạn; từ chối token đã `consumedAt`; từ chối token không tồn tại.
- Integration PostgreSQL thật: đăng ký tạo đúng `User` + `EmailVerificationToken` trong DB; verify-email chuyển đúng `status`; duplicate email bị chặn ở DB constraint qua đúng đường API (không chỉ đơn vị).
- Contract test (MSW) cho `resend-email-adapter`: success, timeout, 429, 5xx, malformed response — xác nhận adapter không throw ra ngoài use case theo cách làm hỏng request đăng ký (đăng ký vẫn nên thành công dù gửi email lỗi tạm thời, hoặc quyết định rõ ràng khác — phải nhất quán và có test, không để hành vi ngầm định).
- Security test: gọi trực tiếp API bỏ qua UI cho cả 2 endpoint; replay token đã `consumedAt` phải bị từ chối; payload abuse (field lạ bị 400); response không lộ `passwordHash`/token thật (`P1-SEC §7`).
- E2E Playwright: đăng ký → nhận (giả lập) link verify → xác minh → xác nhận trạng thái UI thành công.
